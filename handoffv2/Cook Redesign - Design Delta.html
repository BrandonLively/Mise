Design delta · cook screen v1 → v2

Cook screen, rebuilt around per-recipe lanes.

The app today ships the original combined cook flow (one interleaved 22-step sequence with Phase 0/1/2 tabs). This document describes the move to the new model: every recipe gets its own independent guide, shared work is hoisted into a shared lane, and a command bar conducts the whole session. This is the what-changes doc; the companion Android Handoff covers the Compose-level implementation.

Status
The existing app matches the original design (see handoff/Claude Code prompt.html). Everything outside the Cook tab — Login, Home/Schedule, Summary, Recipe drill-down, theme, navigation, auth, data sync — is unchanged. This delta touches the Cook tab only (plus one small addition to the Schedule tab).
Data update · cook-card v3 (2026-06)
Since this delta was first written, the card moved to cook-card.v3: each recipe is self-contained (its own misePhase + cookPhase), with no shared cookPlan and no server-authored shared data. The Shared lane is generated app-side from the recipes in the current plan — by design, so the user can build custom local plans from recipes of any week. The UI in this doc is unchanged; only "where shared work comes from" changes — see Data shape implications (rewritten) below.

The change in one breath

The old Cook screen showed one merged timeline of all four recipes' steps, ordered by clock time, walked with a single swipeable card. The new Cook screen shows one lane per recipe, each an independent guide you advance on its own, with work common to multiple recipes pulled into a dedicated shared lane. A command bar at the top toggles which lanes are visible and tracks running timers. This applies to both the Mise and Cook stages, switched by a toggle.

Mental model: combined → per-recipe

AspectOriginal (v1)New (v2)
Unit of progressOne global step index across all recipes (22 steps)One step index per recipe, advanced independently
OrderingSteps interleaved by clockTimeEach recipe is its own clean sequence; no cross-recipe interleave
Multi-taskingImplicit — the merged timeline jumps between recipesExplicit — lanes sit side by side; you choose which to advance
Shared workAppears as ordinary steps in the timelineHoisted into a shared lane, done once, split across recipes
Clearing finished recipesn/a (single flow)Finishing a recipe removes its lane; chip stays in the bar to re-open
Primary devicePhone-first, tablet adaptiveTablet-first (3 lanes per view); phone is a follow-up

Phases: three tabs → toggle (Phase 0 folded into Cook)

The original Cook screen had a 3-segment phase control: Phase 0 (Kickoff) · Phase 1 (Mise) · Phase 2 (Cook). In the new model:

  • merged into Cook Phase 0 — long-running tasks (start marinade, move avocados to ripen, get rice going) are now the leading steps of each recipe's cookPhase, flagged cookStep.backgroundable=true — not a separate phase or a Schedule item. The app surfaces them first in each recipe's cook lane; cross-recipe ones (e.g. rice) are hoisted into the shared cook lane by the app's derivation.
  • becomes a toggle With Phase 0 absorbed, only Mise and Cook remain — so the 3-segment control becomes a simple Mise / Cook toggle in the title row.
Note · independent per-phase state
Which lanes are visible must be tracked separately for Mise and for Cook. Opening the Chicken lane in Cook must NOT open it in Mise. Model it as two sets (or Map<Phase, Set<LaneId>>).

Side-by-side: old vs new

Cook phase

Carried over from v1 keep: the warm-paper theme, recipe color coding, the step-card task as bulleted lines, the "Meanwhile / running in background" block, the JSON-driven step timer concept, the scrollable-card fade indicator.

Gone remove: the single full-bleed swipe card, the global progress bar, the bottom filmstrip of all 22 steps, the merged step counter.

Mise phase

From v1: the old Mise was a single flat checklist of all 9 bowls ("least-to-most odoriferous"). Now: bowls are grouped per recipe into lanes, with shared bowls in the shared lane. The check-to-complete idea is kept and extended with collapse-on-check (a checked bowl shrinks to bowl number + name to reclaim space).

New: the command bar

A horizontal control strip below the title, split into two groups by a divider:

  • Recipes (left) — a chip per recipe plus a Shared chip. Tapping a chip shows/hides that lane and scrolls it into view (the bar doubles as a pager). Each chip carries a status: queued (outline, muted), in-progress (filled wash, accent dot, progress like 5/9), done (dimmed, green check, strikethrough). The Shared chip shows a count (1/2 steps, or checked-bowls in Mise).
  • Timers (right) — running timer chips (mm:ss + title + recipe color), or "None running". Tap a chip to dismiss.

New: lanes (cook + mise)

A lane is a fixed-width column (3 fit the viewport; more scroll horizontally with snap). Common anatomy: header (recipe identity + status label + progress dots), body (scrollable), footer (controls). The body and footer differ by phase:

Cook laneMise lane
BodyOne step card at a time (current step)Vertical checklist of all the recipe's bowl cards
FooterBack · Next step (last step → Done · finish, which removes the lane)None — you tick bowls down the column
Done stateAll steps completeAll bowls checked

New: the shared lane

Work common to multiple recipes is computed by the app from the recipes in the current plan (not authored on the card) and rendered in a dedicated lane with neutral/accent styling (not a single recipe color) and the participating recipe emojis. Examples: cook the rice (🍗+🍤 — two recipes whose backgroundable rice steps share ingredientId+preparation); a shared diced-onion bowl in Mise (the same (ingredientId, unit, preparation) across recipes, quantities summed). In Cook the shared lane steps sequentially (back/next); in Mise it's a checklist like any lane.

Data shape implications

  • Shared work is app-generated, NOT authored. v3 has no sharedWith on steps and no array forRecipeId on bowls — and we are not adding them. Each recipe arrives self-contained; the app derives the Shared lanes from the recipes in the current plan: mise by merging bowl ingredients on (ingredientId, unit, preparation), cook by grouping backgroundable steps that share an ingredientId+preparation. This is deliberate — keying off canonical ingredientId lets shared work be computed for any recipe set, including custom cross-week plans, with nothing to author per week.
  • Per-recipe cook sequences are already grouped. Steps live in recipe.cookPhase.steps — no grouping by recipeId needed. A no-cook recipe (chia) has a minimal cookPhase (a single assemble/chill step): render a trivial lane or hide it; it still has Mise bowls.
  • Phase 0 is a per-step flag now. Long-running kickoffs are the leading steps of each cookPhase, marked cookStep.backgroundable=true (with a timer). The app surfaces them first; cross-recipe ones (e.g. rice) fall out of the shared-cook derivation above. No distinct phase, nothing on the Schedule tab.
  • Ingredient ids must be canonical. The cross-recipe (and cross-week) mise merge keys on ingredientId, so the same real ingredient uses the same slug on every card (a shared exporter-side vocabulary guarantees this). Composite ids (holy-trinity) won't merge — expect atomic ones.
  • Timer field: step.timer = {label, durationSeconds} (v3 names it label).

Behavior notes for the build

  • Phase 0 lives in Cook — long-running kickoff tasks render within the cook lanes (per-recipe or shared), not as a separate phase or on the Schedule tab.
  • Per-phase lane visibility — independent sets for Mise and Cook (see callout above).
  • Default visible lanes — show in-progress recipes (≈3) by default; queued/done are one tap away in the bar.
  • Finish clears the lane — "Done · finish" marks the recipe complete and removes its lane; its chip stays (dimmed + check) to re-open.
  • Collapse on check (mise) — a checked bowl collapses to number + name; tap again to expand/uncheck.
  • Command bar is the pager — tapping a chip scrolls its lane into view (use a scroll-to-offset, not scrollIntoView on Android equivalents).
  • Tablet-first — design targets 3 lanes per view at tablet width; a phone treatment (1 lane at a time, chips as a top selector) is a later pass.
